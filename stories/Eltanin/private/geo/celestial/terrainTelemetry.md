# Телеметрия процедурного рельефа Eltanin

Базовый синхронный замер выполнен 10 сентября 2026 года; асинхронный повтор и
визуальная проверка движения — 11 сентября. Debug-сборка MSVC, стационарная
камера, 180 кадров, seed 7. Значения предназначены для поиска узких мест и
сравнения итераций, а не как финальный production-бюджет.

## Что измеряется

- `reliefOf()` как общий эквивалент одного `height()` sample;
- CPU-время `buildPatch()` без загрузки на GPU и создания scene actor;
- фактическое число height samples внутри каждого patch;
- успешные создания и перестроения patch по кадрам;
- активные patch по уровням LOD;
- пиковый логический объём временного CPU mesh;
- расчётный payload активных GPU-буферов;
- внешние физические height/surface queries и отдельные altitude queries.

Статистика печатается каждые 60 вызовов `Planetoid::update`. Таймер sample
использует `std::chrono::steady_clock`; его собственная стоимость входит в
профилируемый прогон. Счётчики объединяются один раз на построенный patch и
безопасны для фоновой генерации.

ёмкость временных векторов одного обычного patch, без оценки поведения heap.

## Async generation

11 сентября terrain переведён на узкую локальную очередь с двумя CPU workers.
LOD selection только формирует актуальный набор ключей. Очередь дедуплицируется
по `PatchKey`, выбирает следующую работу по расстоянию до камеры с небольшим
штрафом за высокий LOD, а не по FIFO. Результат имеет revision: устаревший
pending/completed удаляется, а результат уже выполняющегося stale job
отбрасывается при возврате. Lifecycle: `pending`, `generating`, `completed`,
`resident`. GPU install остаётся в `Planetoid::update` и ограничен четырьмя
commit за кадр. Новые патчи сначала загружаются скрыто; полный согласованный
LOD-набор публикуется атомарно, поэтому во время асинхронного перехода не
возникают щели и полосы на границах патчей. Деструктор runtime останавливает
очередь и join-ит оба worker.

До атомарной публикации результат каждого commit становился видимым сразу.
При смене LOD это смешивало участки с разными наборами граничных индексов и
проявлялось длинными белыми/чёрными полосами. Переключение диагностического
вида временно исправляло кадр, потому что принудительно пересобирало меши.
После перехода на скрытый staging дефект не повторился при движении камеры;
это подтверждено пользователем 11 сентября.

## Вывод

Главный риск — не постоянная память, а синхронная генерация. При стационарной
камере первый update создал все 123 patch сразу. Сумма средних времён CPU-build
даёт около 3.2 секунды работы, сконцентрированной в одном стартовом кадре.
После стабилизации камеры churn отсутствовал, поэтому p95 созданий на кадр
равен нулю, а max сохраняет стартовый всплеск 123.

Стартовый синхронный spike устранён. Следующий расширенный тест — быстрый полёт
через границы LOD для нагрузки stale/discard path. Отдельно нужен warm benchmark
`reliefOf`, чтобы отделить обычный sample от холодного создания каталогов.
